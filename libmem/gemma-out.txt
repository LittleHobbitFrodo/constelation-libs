This request requires moving beyond simple list traversal and adopting techniques used by operating system kernel allocators. To achieve $O(\log N)$ time complexity for allocation (finding space) and deallocation (merging), we must maintain two interconnected indices over the free memory blocks.

We will transition from a single index based on physical location to a composite structure: a Physical Map for adjacency checks, and a Size Index for fast searching by capacity.

🏆 Revised Data Structures (Dual-Index Approach)
The allocator now maintains two primary data structures:

1. The Physical Map (free_map)
This map remains responsible for determining physical neighbors and is crucial for the $O(\log N)$ merging step.

Structure: std::collections::BTreeMap<PageOffset, ExtentLength>
Key: Start Page Offset of a free extent.
Value: Length (in pages) of the free extent.
Purpose: To check if an adjacent block starts/ends at a specific page boundary (adjacency lookup).
2. The Size Index (size_index)
This index allows us to quickly query for available blocks that meet a minimum size requirement, enabling $O(\log N)$ Best-Fit allocation search instead of linear scanning.

Structure: std::collections::BTreeMap<ExtentLength, std::collections::BTreeSet<PageOffset>>
Key: The size/length of the free extent.
Value: A set (BTreeSet) containing all starting page offsets that have this specific length. (Using a BTreeSet keeps the starts ordered, which can be useful for deterministic behavior.)
Purpose: To find the smallest available block $\ge$ requested size efficiently.
The Allocator Context
pub struct ExtentAllocator {
    // 1. Physical Map: Start -> Length (For adjacency checks/merging)
    free_map: std::collections::BTreeMap<PageOffset, ExtentLength>,
    
    // 2. Size Index: Length -> Set<StartPages> (For fast capacity search)
    size_index: std::collections::BTreeMap<ExtentLength, std::collections::BTreeSet<PageOffset>>,

}
⚙️ Revised Algorithms and Complexity Analysis
I. Allocation (allocate(size_in_pages)) - Best-Fit
Instead of simply taking the first block (First-Fit), we implement Best-Fit. This minimizes fragmentation and requires a significantly faster search algorithm than $O(N_{extents})$.

Time Complexity Target: $O(\log N)$ or $O(\log^2 N)$.

Procedure:

Search by Size (BTreeMap Traversal): Iterate through the keys of size_index starting from size_in_pages. Since BTreeMap is ordered, the first entry we find will be the smallest available block size ($\ge$ required size).
Find Candidate: Get the key $L_{best}$ and retrieve the set of start pages $S$. Pick an arbitrary start page $P_{start}$ from $S$. This gives us our best-fit candidate: $(P_{start}, L_{best})$.
Handle Failure: If no such entry exists, return None.
Update (Splitting):
Old Entry Removal: Remove $(L_{best}, P_{start})$ from both indices:
Remove $P_{start}$ from the set associated with $L_{best}$ in size_index.
If the set for $L_{best}$ is now empty, remove $L_{best}$ from size_index entirely.
Allocation: The allocated block is $(P_{start}, \text{size})$.
Fragment Handling: Calculate $\text{fragment} = L_{best} - \text{size}$.
If $\text{fragment} > 0$: Insert the resulting fragment into both indices:
free_map: Update $P_{start}$'s entry to reflect the remaining length, or insert a new map entry if we split from one end. (Requires careful bookkeeping).
size_index: Insert $\text{fragment}$ as the new key, and add the fragment's starting page $P'_{start}$ to its associated set.
Complexity Analysis: The primary cost is iterating over size_index. Because we are doing a logarithmic search (finding the smallest available size $\ge$ required size) followed by constant-time index updates, the complexity remains $O(\log N)$, where $N$ is related to the number of distinct free block sizes or total extents.

II. Deallocation (free(start_page, length)) - Coalescing/Merging
The merging logic remains fundamentally based on physical adjacency and relies primarily on free_map's ordering property. We must ensure that every update to the physical arrangement results in updates to both free_map AND size_index.

Time Complexity Target: $O(\log N)$. (No change, but this is already optimal for this operation).

Procedure:

Identify Boundaries & Check Neighbors: Use the current free_map state to check the left and right neighbors of the block $(P_{start}, L)$.
Calculate Merged Block: Determine $(\text{NewStart}, \text{NewLength})$ by merging up to three blocks (Left Neighbor $\rightarrow$ Newly Freed $\rightarrow$ Right Neighbor).
Cleanup Phase (The Critical Step): For every block being merged/removed:
Let $(S_{old}, L_{old})$ be the block being removed.
Update size_index: Remove $S_{old}$ from the set associated with $L_{old}$. If the set becomes empty, remove $L_{old}$ entirely.
Update free_map: Remove $(S_{old}, L_{old})$ from free_map.
Insert Merged Block: Insert $(\text{NewStart}, \text{NewLength})$ into both indices:
Add $\text{NewStart}$ to the set under $\text{NewLength}$ in size_index.
Insert $(\text{NewStart}, \text{NewLength})$ into free_map.
Complexity Analysis: All operations (finding neighbors, map lookups, set insertions/removals) are inherently based on logarithmic tree traversals. Thus, the complexity remains $O(\log N)$, achieving high performance regardless of fragmentation level.

📈 Summary of Time Complexity Improvement
Operation	Old Complexity	New Complexity (Dual-Index)	Improvement Factor
Allocation	$O(N_{extents})$ (Worst Case Linear Scan)	$O(\log N)$	Significant (Scales logarithmically rather than linearly with fragmentation).
Deallocation	$O(\log N)$ (Optimally fine)	$O(\log N)$	Maintained optimal performance.
By adding the SizeIndex, we transform the bottleneck operation (Allocation) from a worst-case linear scan into an efficient logarithmic search, making the allocator highly scalable even under extreme fragmentation pressure.

This detailed algorithm description uses advanced computer science concepts. To make it "human readable," we need to discard the academic jargon ($\text{BTreeMap}$, $O(\log N)$) and focus on the function and analogy of what is happening.

Here is the explanation, framed around the goal and the efficiency gain.

🌳 The Point of the Algorithm: Solving Fragmentation
Imagine a massive parking lot (your memory pool). You are managing many cars (the free blocks/extents).

Over time, you park and unpark cars repeatedly. Soon, instead of one large empty area, you have dozens of tiny isolated gaps between parked cars. Even if those tiny gaps add up to enough space for a bus, you can't use it because the bus needs one continuous, huge spot.

This problem is called External Fragmentation. It’s not that you ran out of total memory; you ran out of contiguous (touching) memory.

The goal of this advanced allocator is twofold:

To always find a gap large enough for the requested size instantly.
To immediately combine any adjacent gaps when they are freed, keeping the free space consolidated into the biggest possible usable chunks.
🔬 How It Works: The Dual-Index System
The reason this system is complex and powerful is that it doesn't rely on a single checklist. Instead, it uses two separate indexes (like two different filing cabinets) to track the exact same information about available space. By using both, we never have to check everything—we can jump right to what we need.

1. Index A: The Physical Map (The Location Book)
What it tracks: Where every free chunk starts and how long it is, purely based on its physical location in the memory strip.
Why it's needed: This index allows us to efficiently answer the question: "Is there a free chunk immediately before or after this spot?" (This is critical for merging/coalescing when we release memory.)
2. Index B: The Size Index (The Capacity Directory)
What it tracks: How many chunks are available of a specific size. It’s grouped by length, and within each group, it lists the starting locations.
Why it's needed: This is the efficiency booster. When you need $X$ amount of memory, we don't want to read every single free chunk in physical order (which might be 10,000 chunks long). We just look up "Any available size $\ge X$" and jump straight to the list.
✨ Operation Breakdown: Allocation (Finding Space)
When you request $X$ amount of memory, we employ a strategy called Best-Fit.

The Process:

We consult the Size Index (Index B) first. We don't look for any chunk $\ge X$; we look for the absolute smallest available chunk that is still big enough. This saves space because we are less likely to waste a massive chunk of memory on a small request.
Once we find that ideal, perfectly sized gap (the Best-Fit), we reserve it.
If the gap was larger than necessary, we "cut" the reserved block out and calculate the remaining piece (the fragment). We then immediately place this new fragment into both Index A (Physical Map) and Index B (Size Index) for future use.
🚀 Operation Breakdown: Deallocation (Giving Space Back & Merging)
When you release a chunk of memory, we don't just dump it back; we must "stitch" it immediately to its neighbors. This is called Coalescing and is the single most important operation for fighting fragmentation.

The Process:

We use the physical location of the newly freed chunk.
We check Index A (Physical Map): Does a free block end right before our spot? If yes, merge it! Does another free block start right after our spot? If yes, merge that too!
If we successfully merged three sections into one massive new section, we perform maintenance on both indices:
Update Index B: We must tell the system: "The old, small chunks at these specific sizes are now gone." (We remove them from the Size Directory).
Update Both Indices: We then insert the single, new, large merged section into both Index A and Index B.
🏎️ Why is This Algorithm Faster? The Complexity Leap
The difference between this advanced system and a simple approach comes down to how we search for answers: linear vs. logarithmic time.

🐢 Simple Approach (Inefficient): Linear Scan
If the memory manager only used one list, finding space would require a Linear Scan. If you have $N$ free chunks, even if the best fit is the second chunk on the shelf, the algorithm has to look at Chunk 1, then Chunk 2, and so on. In the worst case (or simply when $N$ is very large), the time needed increases proportionally with every single gap created ($O(N)$).

🚀 Advanced Approach (Efficient): Logarithmic Jump
By using two indexed maps, we skip the linear scan entirely. This is similar to using a modern smartphone's search bar or a phone book: you don't read every name; you jump directly near the relevant section.

Instead of checking $N$ gaps, we perform operations that take time proportional to $\log N$.
This means that even if your memory pool grows massively and becomes millions of fragmented pieces (a huge $N$), the time it takes for the allocator to find a perfect chunk only increases slightly.
In short: The dual indexing system allows us to make critical decisions about where space is available by doing instantaneous "jumps" into data, rather than slow, piece-by-piece reading.

❓ Can It Work? Conceptual Overview
Yes, it can work, but we are fundamentally changing how the caller interacts with us. The current allocation model assumes that when you call allocate(N), you get $N$ pages, and that entire region must be treated as one unit until you call free on the full $N$.

If a program wants to free only a portion of an allocated chunk (say, freeing bytes 8KB-2MB out of a 2MB block), it can no longer rely on simple memory pointers. The calling code must explicitly track and communicate:

The absolute physical start page address of the partial region being freed.
The precise length of that partial region (in pages).
If the caller provides these two pieces of information, we simply treat this request as if a brand new free chunk has appeared in memory.
